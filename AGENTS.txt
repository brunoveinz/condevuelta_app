1. WHAT CONDEVUELTA IS
----------------------
Condevuelta is a SaaS platform for returnable container ("envase") management:
inventory, loans (prestamos), returns (devoluciones), movements between nodes,
audits, deliveries and reporting. Domain: reverse logistics / circular economy.
Users: foodservice companies, restaurants, logistics operators. Country: Chile.

3. BACKEND FACTS THE MOBILE APP DEPENDS ON (from ../web)
-------------------------------------------------------
Stack: Django 5.0, Django REST Framework 3.14, drf-spectacular (OpenAPI 3),
Django Channels + Daphne (ASGI/WebSockets), Celery + Redis, PostgreSQL,
AWS S3 for media. Deployed on Heroku. Production site: https://condevuelta.cl

Authentication
  - Web uses Django sessions. The API uses DRF Token auth.
  - Get a token:  POST /api-token-auth/   body: {"username": ..., "password": ...}
                  -> {"token": "..."}
  - Send it on every request:  Authorization: Token <token>
  - There is no JWT/refresh flow. Tokens don't expire on their own.
  - Some API views declare authentication_classes = [SessionAuthentication]
    or none at all. Check each endpoint before assuming it accepts a token.
  - Native apps don't need CORS. The backend has no django-cors-headers.
    Only add it if a web-based client (e.g. Expo web) needs it, and only
    with the user's approval (see dependency policy).

API conventions
  - Prefix: /api/  (a few routes use /api/v1/ and /api/v2/ and aren't uniform)
  - Pagination: PageNumberPagination, PAGE_SIZE = 10
    -> responses look like {"count", "next", "previous", "results"}
  - OpenAPI schema: /api/schema/  (Swagger: /api/schema/swagger-ui/,
    ReDoc: /api/schema/redoc/). Restricted to the "condevuelta" group.
    Prefer generating/deriving client types from this schema over
    hand-writing them.
  - Error messages from the API are in Spanish.
  - Timezone: America/Santiago. Send and parse datetimes as ISO 8601.

Roles (Django groups). Access control is group-based. After login the web
redirects each group to its own home. The mobile app should do the same.
  - condevuelta      Internal Condevuelta team        -> dashboard
  - administradores  Internal admins
  - operadores       Store/local operators (OperadorLocal model)
  - representantes   Client company representatives  -> representantes panel
  - supervisores     Supervisors                     -> supervisores panel
  - clientes         End customers                   -> clientes view
  DRF permission classes: IsCondevueltaMember,
  IsCondevueltaMemberOrRepresentante (../web/condevuelta/permissions.py),
  IsOperatorOfLocal (../web/fidelizacion_local/api/permissions.py).
  Most existing API endpoints are IsCondevueltaMember-only. Operator and
  representative flows may need new endpoints (see section 5).

Relevant existing endpoints (non-exhaustive; always verify in the code or schema)
  envases        /api/read-qr/, /api/create/, /api/retire/broken/container, ...
  prestamos      /api/crear-prestamo/
  movimientos    /api/movimiento/, /api/nuevomovimiento/,
                 /api/nuevomovimiento/batch/, monthly metrics under /api/v1/movimientos/
  locales        /api/v1/locales/..., /api/v2/locales/local/{deliveries,returns,
                 stock,cementery}/<local_id>/
  notificaciones /api/v1/notificaciones/...
  delivery       /api/retirosDelivery/            (DRF router)
  local apps     /api/local-containers/, /api/local-container-types/,
                 /api/local-loans/, /api/clients_store/   (DRF routers)
  fidelizacion   /api/fidelizacion/... (loyalty cards, Apple/Google Wallet passes)
  validation     /api/validar/envase/, /api/validar/suscripcion/
  Each Django app registers its routes in ../web/<app>/api/urls.py, included
  from ../web/condevuelta/urls.py.

Other backend features worth knowing
  - QR codes are central: containers are identified by QR/barcode
    (qr_manager, envases/read-qr). Camera scanning will be a core mobile feature.
  - AI chatbot over WebSocket (Django Channels), app condevuelta_ai, route
    /chatbot/. OperadorLocal users get a reduced tool set.
  - Apple Wallet / Google Wallet passes and APNs keys already exist for the
    loyalty module (fidelizacion_local, django-walletpass, aioapns).
    There is NO general mobile push infrastructure yet (no device-token model,
    no FCM).
  - Media (images) is served from AWS S3.

5. RULES FOR AGENTS
-------------------
Language
  - Code (identifiers, comments, docstrings, commit messages): ENGLISH.
  - User-facing text (labels, messages, placeholders): SPANISH (Chile).
  - Legacy backend code is in Spanish. Don't rename it. Just consume it as-is.

Dependencies (CRITICAL, same policy as ../web)
  - NEVER install or add a dependency (npm, pub, pod, gradle, pip...) without
    explicit user authorization. Ask first and explain why.

Backend boundary
  - Work inside this directory by default.
  - Do NOT modify ../web unless the user explicitly asks for it. If the app
    needs a new or changed endpoint, describe it (method, path, payload,
    permissions) and wait for approval.
  - When backend work is approved, follow ../web/AGENT.md strictly:
    APIView/ViewSet + DRF permissions, routes in <app>/api/urls.py,
    transaction.atomic() for multi-write operations, select_related /
    prefetch_related, type hints and docstrings, tests in the app's tests.py.
  - NEVER run the ../web test suite (pytest). Bruno runs tests manually.
    Write the tests and tell him which command to run.

Security
  - Never hardcode credentials, tokens or API keys. Never commit .env files.
  - Store the auth token in the platform's secure storage (Keychain /
    Keystore), never in plain storage.
  - Don't read or copy values from ../web/.env or ../web/certs.

General
  - Use environment-based config for the API base URL (local:
    http://localhost:8000, prod: https://condevuelta.cl).
  - Handle 401/403 globally: 401 -> back to login, 403 -> "sin permisos" screen.
  - Handle paginated lists with infinite scroll / "load more" on top of the
    {count, next, previous, results} format.
  - Plan for poor connectivity (operators work in stores and plants):
    clear loading/error states, safe retries, and no duplicated writes
    (movements, loans).


6. LOCAL SAAS CUSTOMER FLOW (what the MVP plugs into)
-----------------------------------------------------
Local (locales.Local) flags: manage_clients, manage_containers, manage_loans,
manage_loyalty, public_signup_token (UUID), trial_ends_at.

Models (all multitenant, scoped to one Local):
  LocalCustomer      clientes_local   full_name, email, phone (unique per local),
                                      is_active. NO Django user / NO login.
                                      One person in 2 locals = 2 records.
  LocalContainerType envases_local    name, 2-letter code, guarantee_value (CLP),
                                      image.
  LocalContainer     envases_local    code (unique), status: available | loaned |
                                      damaged | lost | retired.
  LocalLoanConfig    prestamos_local  max_loan_days (7), max_active_loans_per_customer
                                      (3), require_guarantee, ...
  LocalLoan          prestamos_local  container, customer (nullable = anonymous),
                                      operator (REQUIRED), due_date (auto),
                                      status: ACTIVE | OVERDUE | RETURNED | LOST |
                                      CHARGED, payment_method (guarantee):
                                      none | cash | card.
  GuaranteePayment   prestamos_local  optional guarantee per loan (Flow/SumUp/cash).
  LoyaltyCard        fidelizacion     points/stamps per customer. A signal awards
                                      points when a LocalLoan becomes RETURNED.
                                      Apple/Google Wallet passes.

Current customer entry points in the web (public, no login):
  /r/<public_signup_token>/     signup form (name + email required, phone
                                optional) -> Flow card vaulting (masked card).
                                clientes_local/public.py
  /loyalty/<local_id>/          loyalty onboarding (QR in store) -> wallet pass.
  POST /api/fidelizacion/onboard/<local_id>/   AllowAny, get_or_create
                                LocalCustomer by phone + LoyaltyCard + WalletPass.
Store QR codes point to those URLs, so the app can parse them to find the local.

How loans work TODAY: only the OPERATOR creates them, in store, by scanning
the container (/api/local-loans/, IsAuthenticated + the operator's local).
Return = operator scans container -> returned_at -> RETURNED -> loyalty points.
The customer never starts anything from their phone.

Backend work the MVP needs (need approval before building in ../web):
  - Customer account + auth: a global customer account (keyed by email)
    linked to many LocalCustomer records; login by one-time email code that
    returns an API token.
  - Local discovery (not registration): public list/search of locals where
    the carnet works (manage_clients + manage_loans = True), with address
    for a map.
  - Automatic link to a local: when an operator scans a carnet in a local
    for the first time, create or reuse that local's LocalCustomer from the
    account data (same idempotency rules as clientes_local/public.py: reuse
    by email or phone within the local). No customer-side form.
  - Customer carnet QR: a payload that identifies the customer without
    exposing raw ids (signed or rotating token), and an operator-side flow in
    the web operator panel to scan it and attach the customer to a new loan.
  - Customer-facing endpoints: my locals, my loans (active / due soon /
    history) across all linked LocalCustomer records.
  - Loans must expose where the container can be returned (today: the
    lending local only), so the app never assumes it.
  - App config endpoint exposing global switches, starting with the card
    switch. Needs a small new config model (no global config model exists
    today; the only ones are per-feature: LocalLoanConfig, BzeroConfig...).
  - Card at ACCOUNT level. Flow card vaulting already exists and must be
    reused: pagos/services.py (ensure_flow_customer, start_card_registration,
    reconcile_card_registration, charge_saved_card), pagos.models.FlowCustomer
    (has_card, card_brand, card_last4), prestamos_local/guarantee.py (charges a
    loan guarantee to the vaulted card). Today FlowCustomer.external_id is per
    LocalCustomer ("local_customer:<id>"); for the app it must be per account
    so one card works in every local. The Flow card page opens in an in-app
    browser and must return to the app via deep link.
  - Not needed for the MVP: customer-initiated requests, loyalty, push.
